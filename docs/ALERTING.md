# Alerting

The alert engine (`app/alerts/engine.py`) decides which detected changes are
worth interrupting a person for, and delivers them. The whole point is signal:
a change reaches a user only when its priority clears the threshold.

## From change to alert

```
DetectedChange (processed = false, is_baseline = false)
        │
        ▼
Insight generated by the impact engine (+ priority score)
        │
        ▼
Score < threshold?  ── yes ─▶ recorded, not alerted
        │ no
        ▼
Alert created (dedupe_key prevents duplicates)
        │
        ▼
Fan out to channels (dashboard, email, Teams, Slack)
        │
        ▼
notification_logs records each attempt
```

## Priority score

`app/intelligence/priority.py` computes a 0–100 score as a weighted sum of six
signals. Each component is normalized to 0–1, multiplied by its weight, and the
total is clamped.

| Signal | Weight | Captured by |
| --- | --- | --- |
| Patent importance | 25 | Substance/product patent, method-of-use code, PTE, delisting, blockbuster drug |
| Sponsor importance | 15 | Match against the major-sponsor reference set |
| Revenue potential | 20 | Blockbuster markers and therapy area |
| Market competition | 15 | Number of challengers / ANDA filers |
| Exclusivity impact | 15 | Remaining exclusivity, expiry proximity, PTE presence |
| Recency | 10 | How recently the change was detected |

**Bands**

| Band | Range |
| --- | --- |
| Critical | 90–100 |
| High | 70–89 |
| Medium | 40–69 |
| Low | 0–39 |

Every component carries a human-readable `reason`, and the full breakdown is
persisted in `alerts.score_breakdown` / `insights.score_breakdown`. A user can
always see *why* something was rated High.

## Event types

| Event | Trigger |
| --- | --- |
| New FTF | A Paragraph IV certification appears |
| FTF withdrawn | A certification disappears from the published list |
| New PTE application | USPTO application list adds a row |
| New PTE certificate | A term extension is granted |
| New PDE entry | An approved active moiety is added |
| Orange Book update | A supplement edition changes products, patents, or exclusivity |

## Channels

Registry in `app/alerts/channels.py`. Each channel is independent; a failure in
one does not block the others, and every attempt is logged.

| Channel | Transport | Configuration |
| --- | --- | --- |
| Dashboard | Stored `Alert` row, polled by the UI | always on |
| Email | SMTP | `SMTP_*` settings; skipped if unset |
| Microsoft Teams | Incoming webhook | `TEAMS_WEBHOOK_URL` |
| Slack | Incoming webhook | `SLACK_WEBHOOK_URL` |

A channel that is not configured reports `skipped`, not `failed`, so the
notification log distinguishes "we tried and it broke" from "we did not try".

The notification gate is `settings.alert_min_priority_to_notify` (default 40 —
the top of the Low band). Insights below it are stored and shown in the change
history but do not notify.

## De-duplication

Each alert has a `dedupe_key` derived from the module, event type, and entity
key. A repeated detection of the same condition updates the existing alert
rather than creating a new one, which keeps the queue meaningful when a source
republishes an unchanged edition.

## Lifecycle

```
open ──▶ acknowledged (acknowledged_by, acknowledged_at) ──▶ resolved
```

`GET /api/v1/alerts/summary` returns counts by priority and status for the
dashboard badge. `GET /api/v1/alerts/{id}/notifications` shows the delivery
history for one alert.

## Tuning

- **Noise too high?** Raise the alert threshold so Medium events stop
  notifying but still appear in the change history.
- **Missing something?** Lower the threshold, or increase the relevant weight —
  for example, raise `market_competition` during a patent-cliff review.
- **One sponsor flooding the feed?** Cap alerts per sponsor per window in the
  engine's creation guard.

Weights and thresholds are constants at the top of `priority.py` and
`engine.py`, overridable per deployment through settings.
